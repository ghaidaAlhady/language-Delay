# Beta deployment: Netlify + Render + Neon

This repository is prepared for a public **beta/demo** deployment with:

- **Netlify** for the React/Vite frontend.
- **Render** for the FastAPI backend.
- **Neon PostgreSQL** for persistent relational data.

The deployment must never upload `backend/.env`, a real API key, a local SQLite file,
generated reports, logs, or test artifacts.

## 0. Verify the repository before publishing

From the original Git working tree, confirm that secrets and runtime data are excluded:

```powershell
git status --short
git check-ignore -v backend/.env
git ls-files backend/.env
git grep -n "AIza"
```

`git ls-files backend/.env` and the key scan must return no secret. Then run:

```powershell
cd backend
.\.venv\Scripts\Activate.ps1
python -m alembic upgrade head
python -m pytest -q -k "not live"
python -m mypy app
python -m ruff check app tests alembic
python -m pip check

cd ..\frontend
npm ci
npm run test
npm run typecheck
npm run lint
npm run build
```

Do not publish if a critical test, typecheck, migration, or build fails.

## 1. Create the Neon database

1. Create a Neon project and database.
2. Copy its connection string from the Neon dashboard.
3. Keep the connection string secret. Do not place it in Git or `.env.example`.
4. Render will receive it as `DATABASE_URL`.

The application normalizes common `postgres://` / `postgresql://` URLs to SQLAlchemy's
asyncpg dialect, translates `sslmode=require` to the asyncpg-compatible SSL option, and
removes the libpq-only `channel_binding` query parameter.

## 2. Deploy the backend on Render

1. Push the reviewed repository to GitHub.
2. In Render, choose **New > Blueprint** and connect the repository containing `render.yaml`.
3. Select the free web-service plan for a beta/demo deployment.
4. Fill the environment variables marked `sync: false`:

| Variable | Required value |
| --- | --- |
| `DATABASE_URL` | Secret Neon connection string |
| `CORS_ORIGINS` | JSON list containing exact HTTPS frontend origins |
| `GEMINI_ENABLED` | `true` to enable Gemini, otherwise `false` |
| `GEMINI_API_KEY` | Secret Gemini key; leave empty when Gemini is disabled |
| `GEMINI_MODEL` | A model available to the Google AI project |
| `GOOGLE_CLIENT_ID` | Optional Google OAuth client ID |

`SECRET_KEY` is generated by Render. Never copy a development secret into production.
Production startup intentionally fails if it receives SQLite, a weak/placeholder secret,
an empty CORS list, a wildcard, or a non-HTTPS/path-bearing CORS value.

### First-deploy CORS order

The final Netlify URL may not exist yet. For the first Render deploy, set a temporary exact
HTTPS placeholder such as:

```text
["https://placeholder.invalid"]
```

After Netlify assigns the real site URL, replace the placeholder with the exact Netlify
origin and redeploy Render. Do not use `*`.

The Render start command runs Alembic migrations before Uvicorn starts. The health check uses
`/api/v1/health/ready`, which verifies database connectivity.

### Free Render cold starts

A free Render web service may sleep after inactivity. The frontend includes a
backend-availability gate that waits and retries for a bounded wake window instead of
immediately showing a login/network error.

## 3. Deploy the frontend on Netlify

1. Create a Netlify site from the same GitHub repository.
2. Netlify reads `netlify.toml` automatically.
3. Before the first production build, add:

| Variable | Value |
| --- | --- |
| `VITE_API_BASE_URL` | Render backend origin, for example `https://smart-guide-language-delay-api.onrender.com` |
| `VITE_BACKEND_WAKE_TIMEOUT_MS` | `90000` for a sleeping free backend |

4. Deploy the site.
5. Copy the exact Netlify origin into Render's `CORS_ORIGINS` JSON list.
6. Redeploy Render, then trigger a final Netlify deploy if the backend URL changed.

The Netlify configuration builds from `frontend/`, publishes `dist/`, adds security headers,
and rewrites SPA routes to `index.html`, so refreshing a nested React Router URL does not
return a Netlify 404.

## 4. Verify the deployed beta

Test in this order:

1. Open the Netlify URL after the backend has been idle.
2. Confirm the Arabic “جارٍ تشغيل الخادم” screen appears and eventually continues.
3. Register and sign in.
4. Add a synthetic test child.
5. Complete an assessment and create the report/PDF.
6. Create the weekly plan, complete activities, and request an alternative.
7. Reach 70% and start reassessment.
8. Refresh during reassessment and confirm the exact same questions remain. The question set
   is persisted in PostgreSQL, not process memory.
9. Test “افهم أكثر”. Gemini quota errors must return deterministic fallback content rather
   than a broken card.
10. Confirm one user cannot access another user's children, plans, reports, or follow-ups.
11. Open a nested frontend URL directly and refresh it to verify the Netlify SPA rewrite.
12. Restart/redeploy the backend and confirm accounts, plans, and frozen questions persist.

## 5. Docker option

`backend/Dockerfile` is repository-root aware and copies both `backend/` and
`knowledge_base/`. The root `.dockerignore` prevents `.env`, databases, virtual environments,
Node dependencies, logs, reports, and test artifacts from entering the image. The container
runs as a non-root user, applies migrations, and exposes a readiness health check.

Render's native Python Blueprint is the primary documented path; Docker is optional.

## 6. Important beta limitations

- A free backend can have a cold start.
- Gemini's free quota can be exhausted; deterministic fallback preserves core functionality.
- The application is supportive and non-diagnostic and does not replace a qualified
  speech-language professional.
- Use an always-on backend, managed backups, monitoring, incident response, and a formal
  privacy/compliance review before treating the system as a production healthcare service.
